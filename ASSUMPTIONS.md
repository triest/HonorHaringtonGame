# ASSUMPTIONS.md - Simulator Approximations

## 1. REPLAY AND SCENARIO ACCURACY [ASSUMPTION] -- UPDATED 2026-09-19, Milestone 12 first slice
* **Originally written before Milestone 1 as a forward-looking plan, now checked against actual code (as its own text asked future passes to do):** the premise "micro-variations... bound to a seed variable" does NOT match reality -- there is NO unseeded (or seeded) randomness anywhere in `simulation/*.gd` today (verified by grep for `randf`/`randi`/`RandomNumberGenerator`/`seed` across the whole directory; every point-defense/sensor/combat resolution formula that exists is a deterministic function of its inputs, per ТЗ §43's own requirement, which this codebase has simply honored throughout rather than needing a seed to enforce it).
* **What replay actually relies on instead (Milestone 12, `replay_log.gd`/`SimulationWorld.start_recording`+`apply_recorded_command`):** since there is no randomness to reproduce, recording (initial scenario setup, already built by a scenario script) + (every command issued, via `_record_command`) + (the fixed timestep, ТЗ §43/§44) is sufficient by itself to reproduce a run exactly, by re-running the simulation from scratch with the same setup and re-issuing the same recorded commands at the same ticks -- proven by `test_replay_log.gd`'s `_test_replay_reproduces_the_original_run`. No seed is actually needed for correctness today.
* `ReplayLog.random_seed` is kept as a field (default 0, settable via `start_recording(seed)`) purely for forward compatibility -- nothing reads it back. IF a future Milestone introduces real seeded randomness (e.g. sensor noise, as this entry originally anticipated), that pass must (a) actually construct a `RandomNumberGenerator` seeded from this field somewhere reachable by the resolvers that would use it, and (b) update this entry again to describe the real mechanism, not treat the field's mere existence as "done".
* Full periodic state snapshots for fast seeking into a long replay (§45's own "if practical" hedge) are explicitly NOT implemented -- would require `to_dict()`/`from_dict()` on roughly two dozen stateful classes across the simulation, a separate pass. Today, "seeking" means replaying from tick 0 via `apply_recorded_command`, which is instant for a short engagement but does not scale to a long multi-thousand-tick scenario without snapshots -- honestly deferred, not forgotten.

## 2. SENSOR TRACKING STATES [ASSUMPTION]
* **Confidence Interpolation:** When a target is obscured by heavy ECM, the simulator interpolates its position based on its last known velocity vector and active acceleration. This creates a spatial displacement between "Sensor Truth" and "Actual Reality" for the AI and Player UI.

## 3. TACTICAL AI PARALLELISM [ASSUMPTION]
* **Reaction Loops:** Tactical AI calculates new flight matrices and targeting distributions on a throttled loop (every 10 simulation ticks) to conserve processing budget during massive missile salvos, simulating command reaction lag.

## Дросселирование двигателя ракеты — допущение модели

Реализовано `MissileState.set_throttle(fraction)`. Модель: константный
"бюджет delta-v" (`base_accel * base_burn_time == throttled_accel *
throttled_burn_time`) — ЭТО ИНЖЕНЕРНОЕ ДОПУЩЕНИЕ, не прямая цитата канона.
Канон подтверждает САМ ФАКТ компромисса (меньше ускорение → больше время
горения/дальность), но не даёт формулу. Разумное физическое приближение
(константный запас топлива/энергии), задокументировано как ASSUMPTION.
Ограничение: throttle можно установить только до начала горения
(вызов `set_throttle()` после старта не поддержан релевантно — можно
вызвать, но `drive_burn_remaining_s` будет сброшен на новый burn_time,
что физически неверно для "уже летящей" ракеты — TODO: либо запретить
throttle mid-flight явной проверкой, либо продумать частичный останов).

## Известная проблема точности на больших дистанциях (НЕ решена)

`ShipPhysicsState.position` — в метрах, реальный масштаб Honorverse
(тысячи-миллионы км). Godot Node3D transform использует float (32-bit)
внутри рендер-слоя — на дистанциях свыше ~10⁵-10⁶ м это может давать
джиттер/потерю точности при рендере (сама физика в `ShipPhysicsState`
считается на float Vector3 тоже, не double — GDScript/Godot Vector3 по
умолчанию single-precision, если явно не собран движок с double
precision build). ТЗ §14 требует "origin rebasing или локальные системы
отсчёта" для больших дистанций — ЭТО НЕ РЕАЛИЗОВАНО. Для текущего
прототипа (дистанции ~10⁴ м) не критично, но это известный технический
долг для реальных боевых дистанций (сотни тысяч - миллионы км).

## Sensors (§23) — первая версия, пороговые числа (по итогам "Седьмая сверка")

заведены нигде в живом коде — `SensorResolution`/`SensorContact`

напрямую через `target.position`) или из `PointDefenseResolution`
(PD по-прежнему проверяет дистанцию напрямую, не через SensorContact).
Это следующий шаг — подключение, а не эта заготовка.

## Терминальная детонация всё ещё по истинной дальности (не по сенсорной оценке)

После подключения сенсоров к наведению (`MissileGuidance.resolve_thrust_direction`)
осталась НЕ решённая асимметрия: `MissileState.integrate()` проверяет
вход во терминальную дальность и взвод боеголовки через
`target.position` (истинную позицию), а не через `sensor_contact`.
То есть ракета может "физически" пролететь достаточно близко и
сдетонировать, даже если её наведение (уже сенсорно-честное) в этот
момент её не видит. ASSUMPTION: оставлено намеренно как временное
упрощение — разделение "физическая близость взрывателя" (обычно
собственный, отдельный от основного радара, ближний датчик
неконтактного взрывателя) от "радар наведения для довода до цели" —
правдоподобно и канонически не противоречиво, но не проверено
источниками. Следующий шаг для честности — либо явно обосновать это
разделение (ближний взрыватель как отдельный сенсор с собственной,
очень малой дальностью), либо тоже завязать на `sensor_contact`.

## Formation-keeping PD-регулятор (Milestone 10 продолжение) — коэффициенты не канон, угловая скорость ведущего не учтена

`_resolve_formation_keeping` (см. ARCHITECTURE.md) теперь считает
`desired_accel = to_station * K_P_STATION + velocity_error * K_D_STATION`
с K_P_STATION=0.02, K_D_STATION=0.9. ASSUMPTION: подобрано так, чтобы
характеристическое уравнение системы (x'' = -K_P x - K_D x') было СИЛЬНО
передемпфировано (коэффициент затухания ζ = K_D/(2*sqrt(K_P)) ≈ 3.18 —
подход без перерегулирования/колебаний), а не через игровое тестирование
или канонический источник — Honorverse не документирует формулу
станционного удержания на уровне управления двигателем. НЕ учтено
(открытый TODO, не скрыто): угловая скорость САМОГО ведущего при
развороте создаёт дополнительную составляющую скорости у офсетной точки
(v = ω × r) для любого члена не в нулевом офсете — сейчас matching идёт
только по линейной скорости ведущего, так что во время манёвра с
разворотом член строя будет по-прежнему слегка "стричь" реальную
станцию, только меньше, чем без matching скорости вовсе. Резервный
ведущий/перестроение при потере текущего ведущего (§33 Formation Leader)
по-прежнему НЕ реализовано — `_resolve_formation_keeping` просто
пропускает строй без ведущего, без выбора преемника; это открытый пункт
для следующего прохода по Milestone 10.

Рабочая ГИПОТЕЗА (не доказана из этой сессии — нет доступа к точной
длительности прошлых сессий/полной истории срабатываний): ни
`create_trigger`, ни планировщик, судя по всему, не гарантируют, что
предыдущий запуск данной scheduled-задачи ЗАВЕРШИЛСЯ до следующего
срабатывания по расписанию. Если один проход когда-либо выполнялся
дольше ~3 часов (например, завис на скачивании Godot-бинарника при
плохой сети, или застрял в долгом тестовом прогоне/git-конфликте),
следующее штатное cron-срабатывание стартовало бы ПАРАЛЛЕЛЬНО с ещё не
завершившимся предыдущим экземпляром — что и дало бы наблюдавшуюся 4
раза подряд картину (два экземпляра сессии активны одновременно над
одной и той же папкой, оба видят и коммитят в один git-репозиторий) без
необходимости в ручных перезапусках задачи пользователем или ошибке в
самом cron-выражении. Это САМОЕ ПРОСТОЕ объяснение, совместимое со
ВСЕМИ фактами, накопленными за 4 прохода (единственный trigger,
корректный cron-интервал, отставание `updated_at` от `last_fired_at`
на секунды объясняется тем, что предыдущий проход вызвал
`update_trigger` в САМОМ КОНЦЕ своей работы, что могло по времени
почти совпасть со СЛЕДУЮЩИМ штатным срабатыванием, если тот проход
действительно занял близко к 3 часам). ОТКРЫТЫЙ ВОПРОС ПОЛЬЗОВАТЕЛЮ
(уточнён, не снят): если проходы этой задачи регулярно занимают
заметную часть 3-часового интервала (или больше) — стоит либо
увеличить интервал cron, либо просто принять эту особенность как
известную и не критичную (общий git-репозиторий, независимые коммиты,
конфликтов пока не наблюдалось). Дальнейшая диагностика без доступа к
полной истории запусков задачи (не только `last_run`) этой сессией
невозможна.

## §29 Formation Orders — execution law и допущения этого прохода

Закрыт пробел "остальные явные §29 Formation Orders (change course/
change speed/... как ИГРОВЫЕ ПРИКАЗЫ) не реализованы". См.
CHANGELOG.md/ARCHITECTURE.md за техническое описание
(`FormationOrder`, `FormationState.current_order`/`order_queue`,
`SimulationWorld._resolve_formation_orders`).

Явно зафиксированные допущения:

* **EXACT-STOP acceleration clamp — ИНЖЕНЕРНОЕ РЕШЕНИЕ, не канон.**
  Приказ выполняется так: ускорение ведущего всегда направлено точно на
  остаточную ошибку скорости (`target_velocity - guide.velocity`), а
  его величина ограничена `min(max_accel, error.length()/dt)`. Это
  гарантирует, что ведущий НИКОГДА не проскакивает цель за один тик
  (новая величина ошибки = старая величина минус пройденное расстояние,
  математически не может стать отрицательной), то есть сходимость
  монотонна и БЕЗ колебаний, без необходимости подбирать
  пропорционально-дифференциальные коэффициенты (в отличие от
  station-keeping'а членов строя, которому потребовался PD-контроллер
  именно потому, что у НЕГО нет "разового приказа с завершением" — цель
  станции бессрочна). Альтернативы (постоянный bang-bang thrust, как у
  disengage/retreat отдельного корабля) были отвергнуты: при типичных
  для этой кодовой базы ускорениях (сотни g) bang-bang проскочил бы
  скромное изменение скорости на первом же тике и начал бы колебаться
  вокруг цели бесконечно (приказ никогда бы не завершался). Нет
  источника Honorverse, описывающего, КАК именно рулевые исполняют
  приказ смены курса/скорости — весь этот механизм ASSUMPTION.
* **"Change course" перенацеливает ВЕКТОР СКОРОСТИ, не носовую
  ориентацию корабля — INTERPRETATION.** См. CHANGELOG.md для полного
  обоснования (согласовано с уже существующей всенаправленной моделью
  thrust в этой кодовой базе). Управление angular_velocity от
  AI/приказов по-прежнему нигде не реализовано в коде — отдельный,
  честно открытый пробел на будущее (если/когда носовая ориентация
  станет геймплейно значимой — арки оружия, sidewalls, сенсорные
  конусы — этот приказ, возможно, придётся расширить, чтобы разворачивать
  и корпус, не только траекторию).
* **heading_tolerance_rad = 0.02 рад (~1.15°), speed_tolerance_mps =
  0.5 м/с — ASSUMPTION константы, без канонического источника.**
  Небольшие "игровые" пороги, чтобы плавающая точка у самой цели не
  оставляла приказ вечно "почти выполненным". Подлежат пересмотру по
  ощущениям геймплея, не привязаны ни к чему в источниках.
* **HOLD_FORMATION как "стоячий" (не завершающийся) приказ —
  инженерный выбор, не канон.** Приказы CHANGE_COURSE/CHANGE_SPEED —
  разовые манёвры с чёткой целью и завершением; HOLD_FORMATION
  концептуально другое — это "прекратить манёврирование", у которого
  нет естественного условия "готово". Реализовано как приказ, который
  каждый тик активно обнуляет собственный thrust ведущего и НИКОГДА не
  снимается сам — снимается только явной заменой (`issue_order_now`)
  или постановкой нового приказа в очередь. Альтернатива (считать
  HOLD_FORMATION мгновенно "завершённым" и просто удалять) была
  отвергнута — тогда он был бы неотличим от "приказов вообще нет", а
  явная разница (нулевой thrust КАЖДЫЙ тик, а не оставление старого
  thrust как есть) — это осознанное отличие "останови манёвр" от
  "приказов не было".
* **`withdraw_orders()` — composite, не новый примитив Kind.**
  §29 перечисляет "withdraw"/"disengage" как отдельные пункты, но они
  здесь честно СОБРАНЫ из двух уже существующих примитивов
  (change_course + change_speed с явно переданным heading, чтобы
  второй приказ в очереди не зависел от фактического состояния
  ведущего на момент СВОЕГО исполнения, а не постройки очереди — см.
  `change_speed`'s `heading_world` параметр в коде). Это НЕ то же
  самое, что §26's существующий `_resolve_damage_response`
  retreat/disengage для ОТДЕЛЬНОГО повреждённого корабля (bang-bang,
  сенсорно-честный, автоматический по здоровью) — этот новый механизм
  ЯВНО выдаваемый формации приказ для ВЕДУЩЕГО, а не автоматическая
  реакция на повреждения. Оба механизма сосуществуют независимо.

Честно НЕ сделано (отдельные, не связанные с этим пробелом gaps,
остаются открытыми): §29 items, требующие контекста цели/оружия
(attack, select target, target distribution, missile use,
counter-missile posture, defensive posture, evasive maneuver);
"change formation" (смена самой геометрии design_offsets на лету, а не
просто движение ведущего); отдельный примитив-конструктор для
"approach" (движение к точке — сейчас можно собрать вручную из
change_course к вычисленному направлению + change_speed, но готового
хелпера нет); многоуровневая иерархия команд §28 (по-прежнему плоская);
управление носовой ориентацией от AI/приказов; ECM не деградирует
точность/захват PD; §25 consumer'ов для COMMUNICATIONS/POWER/
STRUCTURAL_INTEGRITY/DEFENSIVE_SYSTEMS нет; Milestone 11+ не начаты.

## §29 "change formation" — допущения этого прохода

Закрыт пробел "change formation (смена самой геометрии design_offsets
на лету) — НЕ реализована", упоминавшийся в нескольких предыдущих
записях подряд. См. CHANGELOG.md/ARCHITECTURE.md за техническое
описание (`FormationOrder.Kind.CHANGE_FORMATION`,
`SimulationWorld._apply_change_formation`).

Явно зафиксированные допущения:

* **Переиспользование station-keeping PD-закона вместо новой "механики
  перестроения" — ИНЖЕНЕРНОЕ РЕШЕНИЕ, не канон.** Нет источника
  Honorverse, описывающего, КАК именно эскадра физически перестраивается
  из одной формации в другую (тайминг, траектории отдельных кораблей,
  синхронизация). Решение "офсет меняется мгновенно, физический долёт
  делает уже существующий контроллер" — не претендует на реализм
  манёвра, только на консистентность с уже принятой моделью
  (§43 simplicity/consistency).
* **`is_complete()`-эквивалент для CHANGE_FORMATION — мгновенный, не
  дожидается физической сходимости.** В отличие от CHANGE_COURSE/
  CHANGE_SPEED (где "приказ выполнен" буквально означает "скорость
  ведущего сошлась к цели"), CHANGE_FORMATION считается выполненным в
  тот же тик, когда офсеты переписаны — "приказ отдан" и "корабли
  физически встали на новые станции" разделены как два разных понятия.
  Обоснование см. ARCHITECTURE.md. Если геймплейно понадобится различие
  ("формация ещё перестраивается" индикатор в UI), его придётся
  добавлять отдельно (проверяя `member.position` каждого члена против
  `member_offsets`), сейчас такого API нет.
* **Калибровка времени долёта — ЭМПИРИЧЕСКАЯ, не тюнинг под целевое
  значение.** С существующими K_P_STATION=0.02/K_D_STATION=0.9 (уже
  принятыми в прошлом проходе, не менявшимися здесь) характеристическое
  уравнение системы (`s^2 + K_D*s + K_P = 0`) даёct два вещественных
  полюса: быстрый (~1.1с постоянная времени) и МЕДЛЕННЫЙ (~43с
  постоянная времени, доминирующий на больших временах). Замеренный
  прогоном полный долёт с ~940м занимает: 10с → прошло всего ~18%
  дистанции; 60с → ~74% дистанции; 120с → ~93%; 200с → ~99%; 300с →
  практически полная сходимость (<1.1м). Тест использует 300с/18000
  тиков как безопасный запас. Если K_P_STATION/K_D_STATION когда-либо
  будут перенастроены (геймплейное решение, не канон — см. предыдущую
  запись про PD-контроллер), это время долёта пропорционально
  изменится, и калибровочный тест может потребовать пересмотра порога.
* **"Не упомянутый в приказе член остаётся нетронутым" — сознательный
  выбор семантики "частичного" приказа, не единственно возможная.**
  Альтернатива (CHANGE_FORMATION всегда описывает ПОЛНУЮ форму строя,
  а отсутствующие в словаре ключи трактуются как "покинуть строй") была
  отвергнута — она сделала бы невозможным "сдвинуть только один фланг"
  без явного повторения офсетов всех остальных кораблей в каждом
  вызове, что не соответствует прочитанному §29 буквально ("change
  formation" — это одна интенция среди списка, не единственный
  универсальный дескриптор всей геометрии).
* **Добавление НОВОГО члена строя через тот же приказ — не отдельная
  "join formation" интенция.** §29 не перечисляет "assign station"/
  "join" как отдельный Kind, и заводить его отдельно ради этого узкого
  случая было бы искусственным дублированием: "переназначить офсет
  корабля, которого раньше не было в списке" и "переназначить офсет
  уже присутствующего корабля" — для `Dictionary.__setitem__` это в
  буквальном смысле одна и та же операция, разделять их программно не
  за что.

## §30/§31 Individual Ship Orders / Individual Override — допущения этого прохода (Milestone 11 начат)

См. CHANGELOG.md/ARCHITECTURE.md за техническое описание
(`IndividualOrder`, `IndividualCommandState`,
`SimulationWorld._resolve_individual_orders`/
`_resolve_individual_orientation_order`).

* **`IndividualOrder` дублирует CHANGE_COURSE/CHANGE_SPEED из
  `FormationOrder` вместо переиспользования — ИНЖЕНЕРНОЕ РЕШЕНИЕ, не
  канон.** См. ARCHITECTURE.md за полное обоснование (риск трогать уже
  протестированный hot-path код `FormationOrder` в том же проходе, что
  вводит новую, ещё не обкатанную концепцию per-ship override).
* **CHANGE_ORIENTATION работает в BODY-frame (локальной системе
  координат корабля), не в world-frame — выведено из фактической
  семантики `KinematicsUtils.integrate_orientation`, не предположено.**
  Композиция `orientation * delta_rotation` (право-умножение) —
  стандартная конвенция для BODY-frame угловой скорости: вращение
  вокруг СВОЕЙ локальной оси не меняет мировое направление этой самой
  оси (ровно так ведёт себя реальный корабль, вращающийся вокруг
  собственной оси через маховики/двигатели ориентации, заданные в его
  собственной системе координат). Формальная проверка: пусть
  `orientation_old` = поворот на 90° вокруг мировой Z, так что локальная
  ось X корабля указывает вдоль мировой Y. Пусть `angular_velocity =
  (1,0,0)` (локальная ось X). `orientation_new = orientation_old *
  delta_rotation`, где `delta_rotation` — поворот вокруг оси (1,0,0).
  Применим `orientation_new` к локальному вектору v_body=(1,0,0):
  `orientation_old * delta_rotation * v_body = orientation_old * v_body`
  (поворот вокруг (1,0,0) не меняет сам (1,0,0)) — т.е. локальная ось X
  корабля (уже указывающая вдоль мировой Y) остаётся указывать вдоль
  мировой Y и после этого тика: поворот "вокруг себя" не сдвинул
  собственную ось вращения. Это именно BODY-frame поведение. Если бы
  `angular_velocity` трактовалась как WORLD-frame, поворот "вокруг
  мировой оси X" сдвинул бы то, куда указывает локальная X корабля
  (которая сейчас = мировой Y) — v_body НЕ остался бы инвариантным.
  **ПОДТВЕРЖДЕНО ЭМПИРИЧЕСКИ**, не только выведено на бумаге:
  `test_individual_orders.gd` включает
  `_test_change_orientation_from_non_identity_orientation_converges_correctly`
  — корабль стартует уже повёрнутым на 90° вокруг мировой Y (носом
  вдоль мировой -X), приказ "смотреть вдоль мировой +Z"; тест прошёл на
  первой же попытке реализации, что подтверждает, что расчёт оси/угла
  в ЛОКАЛЬНОЙ системе координат (транспонирование мировой цели в
  локальный кадр через `orientation.inverse() * target_facing_world`
  ПЕРЕД вычислением оси вращения) — правильный подход. Это САМЫЙ важный
  тест этого прохода: тест с identity-ориентацией (мировая и локальная
  система совпадают) прошёл бы ДАЖЕ при перепутанной конвенции кадра —
  только non-identity-тест реально дискриминирует ошибку.
* **Существующая формула станционного удержания
  `guide.angular_velocity.cross(offset_world)` (Milestone 10,
  предыдущий проход) технически смешивает BODY-frame omega с
  WORLD-frame offset — НЕ исправлено в этом проходе, честно
  зафиксировано как отдельный, не связанный с этим проходом
  вопрос.** Она уже прошла собственные тесты (см. предыдущую запись
  "Угловая скорость ведущего в station-keeping") и трогать её здесь не
  входило в scope. Возможные объяснения: (а) формула — сознательное
  приближение, верное лишь при ориентации, близкой к identity
  (типичный случай для тестовых сценариев без резких манёвров); (б)
  реальная ошибка, скрытая тем, что тесты не проверяли ведущего с
  сильно не-identity ориентацией. Открытый вопрос для будущего прохода
  — НЕ затронуто/не исправлено здесь, так как выходит за рамки §30/§31.
* **Честно найденная и исправленная ошибка — в ТЕСТЕ, не в коде.**
  Первая версия `_test_change_orientation_handles_180_degree_reversal`
  давала кораблю 600 тиков (10с) на разворот на 180°, но при
  `max_angular_speed_rad_s = 0.3` рад/с полный разворот на π радиан
  требует МИНИМУМ π/0.3 ≈ 10.47с — тест не мог пройти физически, вне
  зависимости от правильности кода. Первый прогон корректно провалил
  именно этот тест (2 FAIL из 36) при 34 успешных, что само по себе
  было полезным сигналом: остальные (90°/identity/non-identity) кейсы
  прошли с первой попытки, подтверждая, что реализация верна, а не
  тест "случайно" зелёный. Исправление — увеличенный бюджет тиков (900,
  ~15с) именно для этого кейса, задокументировано в самом тесте.
* **Точно антипараллельный (180°) случай — произвольная ось fallback,
  ASSUMPTION, не канон.** Нет канонической "правильной" оси для разворота
  на 180° без дополнительного ограничения по крену (roll) вокруг
  продольной оси — проект нигде не моделирует крен/roll в принципе
  (не только здесь), так что выбор оси (`forward.cross(UP)`, либо
  `forward.cross(RIGHT)` как fallback fallback'а если даже это
  вырождено) — инженерный, не числовое допущение.
* **CHANGE_ORIENTATION считается "исполненным" мгновенно по углу, не
  дожидаясь остановки вращения отдельным условием — тот же exact-stop
  clamp принцип, что и CHANGE_COURSE/CHANGE_SPEED.** На тике, когда
  `angle_err <= orientation_tolerance_rad`, `angular_velocity`
  обнуляется В ТОТ ЖЕ ТИК (не следующий) — иначе корабль продолжил бы
  вращаться по инерции мимо цели, так как ничто больше не управляет
  `angular_velocity` для этого корабля (в отличие от `commanded_thrust_
  local`, которое может быть переписано другой системой на следующем
  тике). Без этого явного обнуления небольшая остаточная угловая
  скорость с последнего "не завершён" тика сохранялась бы бесконечно
  (`angular_velocity` не гасится никаким трением/демпфированием нигде в
  проекте) — вечный медленный дрейф ориентации, честно предотвращённый
  здесь.
* **§31's "account for communication limitations" (аналог §33's
  `COMMAND_TRANSFER_DELAY_S`) намеренно НЕ реализован для
  индивидуальных приказов в этом проходе.** Индивидуальный приказ,
  выданный через `issue_individual_order(_now)`, вступает в силу
  МГНОВЕННО, в тот же тик, когда исполняется `_resolve_individual_orders`

  моделирует эту задержку только для recognition/succession ПОСЛЕ
  потери ведущего (крупное событие с реальной неопределённостью для
  экипажа), а не для рутинной выдачи приказа отдельному кораблю в

## §30 "target"/"target priority"/"weapon mode" — допущения этого прохода (ShipCombatDirective)

* **`weapons_free` — единый флаг на энергооружие И ракетные пуски.**
  ASSUMPTION/INTERPRETATION, не канон: ТЗ §30 перечисляет "weapon mode" и
  "missile launch" отдельными пунктами списка, что могло бы означать два
  независимых fire-control переключателя. Сделан один общий флаг —
  инженерное упрощение этого прохода, честно задокументированное, не
  скрытое; разделение на `weapons_free`/`missiles_free` тривиально
  добавить отдельным проходом, если геймплей потребует "держать лучи, но
  продолжать пускать ракеты" (или наоборот).
* **Fallback на автоматический выбор при невалидной designation — не
  "held fire".** Когда `manual_target_ship_id` указывает на цель, которая
  уничтожена, вышла из зоны видимости датчиков, или никогда не была
  hostile, `SimulationWorld._resolve_weapon_target` откатывается на
  прежнее автоматическое `TacticalAI.select_weapon_target` (ближайший
  usable hostile), А НЕ прекращает огонь. Инженерное решение
  (ASSUMPTION), не канон: альтернатива "designation невалидна => держать
  огонь, пока не переназначат вручную" тоже была бы честной и, возможно,
  ближе к реальной военной доктрине "не стрелять без приказа" — открытый
  вопрос для будущего геймплейного решения, см. ARCHITECTURE.md.
* **Designation и weapons_free применяются МГНОВЕННО, тем же тиком, без
  задержки передачи команды.** Тот же честно повторяющийся пробел, что и
  у §30 kinematic-приказов и §31's "account for communication
  limitations" из прошлого прохода (см. предыдущую запись "§31's 'account
  for communication limitations' намеренно НЕ реализован...") — не
  расширено и не исправлено здесь, т.к. выходит за рамки этого слайса.
* **Point Defense сознательно не подключена к ShipCombatDirective.**
  PD выбирает цель по принципу "какая РАКЕТА реально атакует ЭТОТ
  корабль" (`TacticalAI.select_pd_target`, угроза-ориентированный выбор),
  тогда как §30 "target"/"weapon mode" — это выбор ВРАЖЕСКОГО КОРАБЛЯ для
  атаки энергооружием/ракетами. Это разные, не взаимозаменяемые понятия:
  "designate target ship X" не имеет прямого смысла для PD (PD не может
  "передумать" стрелять по конкретной ракете, летящей в тебя, в пользу
  ракеты, летящей в кого-то другого, без изменения самой природы
  защитного огня). §29/§30's "counter-missile policy"/"point-defense
  policy" остаются отдельным, честно не реализованным пунктом.
* **`select_directed_weapon_target` не делает собственного fallback-
  решения — оно живёт в `SimulationWorld._resolve_weapon_target`.**
  Разделение ответственности сохранено намеренно (тот же принцип, что и
  у `select_weapon_target`/`select_pd_target`): TacticalAI остаётся
  чистой stateless функцией выбора цели БЕЗ knowledge о политике отката,
  SimulationWorld — единственное место, решающее ЧТО делать при разных
  исходах выбора.

## §25/§31 Communication-delayed individual orders — допущения этого прохода (`transmit_*`)

См. CHANGELOG.md/ARCHITECTURE.md за техническое описание
(`_pending_command_transmissions`, `_resolve_pending_command_transmissions`,
`_individual_order_transmission_delay_s`).

* **Базовая задержка (1с при здоровой связи) — ASSUMPTION, не канон.**
  Как и `COMMAND_TRANSFER_DELAY_S` (3с) до неё, нет канонической
  Honorverse-цифры для "сколько времени занимает передать рутинный
  приказ отдельному кораблю в пределах тактической дистанции формации
  при исправной связи". Выбрана явно МЕНЬШЕ, чем `COMMAND_TRANSFER_DELAY_S`
  — инженерное решение, что "распознать потерю ведущего и провести
  процедуру передачи командования" (крупное, неопределённое событие) и
  "передать рутинный приказ по уже установленному каналу связи"
  (механическая задержка релейной цепочки) должны быть РАЗНЫМИ по
  порядку величины, а не одним и тем же числом.
* **Задержка зависит от COMMUNICATIONS корабля-ПОЛУЧАТЕЛЯ приказа, не
  корабля-отправителя (флагмана/командующего).** ASSUMPTION: реальная
  система связи — канал между двумя кораблями, деградация могла бы
  зависеть от ЛЮБОЙ стороны (или geometрии/дистанции, которая тоже не
  учтена). Выбран более простой вариант "деградация принимающей стороны"
  — соответствует §25's worked example буквально ("communications
  damage → degraded command/reporting" — именно у ТОГО корабля, чья
  подсистема повреждена), не потому что это единственно верная модель.
  Дистанция/geometрия между кораблями как фактор задержки НЕ
  рассмотрена — честно открытый вопрос.
* **Формула — floor-делённая (`base / max(condition, floor)`), тот же
  стиль, что у `PointDefenseMount.effective_reaction_time_s()` —
  сознательно НЕ капped сверху (в отличие от structural-vulnerability
  идеи, которая была РАССМОТРЕНА и ОТКЛОНЕНА в пользу этой задачи в этом
  же проходе, см. следующий пункт) — задержка приказа, в отличие от
  урона за тик, не рискует "убежать" неограниченно за один тик (худший
  случай: приказ очень долго не доходит, что само по себе честный
  игровой эффект "потеря связи важна", не баг runaway-типа).
* **Почему НЕ STRUCTURAL_INTEGRITY/POWER/DEFENSIVE_SYSTEMS в этом
  проходе — сознательный отказ, не забывчивость.** Рассматривался
  вариант "STRUCTURAL_INTEGRITY-множитель повышенной уязвимости к
  урону" (масштабировать входящий урон по мере деградации
  STRUCTURAL_INTEGRITY), но `ship_subsystems.gd`'s собственный class doc
  уже явно фиксирует, почему это было отложено предыдущим проходом:
  "STRUCTURAL_INTEGRITY (HullState is still the single-scalar §58
  placeholder pool ТЗ §59 requires replacing before Definition of Done
  -- wiring STRUCTURAL_INTEGRITY meaningfully needs that replacement
  first, not a quick shim)". Множитель урона поверх временной
  HullState-заглушки — ровно тот "quick shim", от которого
  предупреждает этот комментарий; решено уважать это предыдущее
  инженерное решение, а не переписать его без замены самого HullState.
  POWER (нет модели энергобюджета) и DEFENSIVE_SYSTEMS (неясно, что это
  физически представляет отдельно от wedge/sidewalls — см. тот же class
  doc) остаются по той же причине: оба требуют СНАЧАЛА построить
  систему, которой ещё нет, а не просто "подключить существующий
  провод" — больше одного прохода, честно отложено, не тихо забыто.
* **Приказ, застрявший в очереди передачи на удалённый/более несуществующий
  корабль, просто никогда не применяется (Callable молча не находит
  корабль, если целевые функции сами проверяют существование — большинство
  из них НЕ проверяют, см. ниже) -- не крашится, не откатывается,
  остаётся честно "потерянным в эфире".** ASSUMPTION: альтернатива
  (отменять зависшие передачи при потере контакта с получателем) не
  реализована -- нет модели "потери контакта" отдельно от удаления
  корабля из мира.
* **`set_ship_target`/`clear_ship_target`/`set_ship_weapons_free`/
  `return_ship_to_formation`/`issue_individual_order_now` по-прежнему НЕ
  проверяют существование `ships[ship_id]`** (как и раньше этого
  прохода) -- `transmit_*` ничего не меняет в этом отношении, тот же
  давно существующий пробел (см. `order_missile_launch`'s собственную
  запись "не проверяется владение назначенной целью формацией/
  иерархией").

## Milestone 12: Replay first slice -- ship destruction was a previously-invisible gap, not a deferred one

Unlike most gaps logged in this file (a feature honestly not started
yet), automatic ship destruction/removal was a case where every
INDIVIDUAL piece already existed and looked correct -- `HullState.
apply_damage()`/`is_destroyed()` worked fine, formation-leader-loss logic
already read `is_destroyed()` correctly -- but nothing in
`SimulationWorld.tick_simulation()` ever actually removed a ship once its
hull reached zero. It would stay in `ships`/`hulls` forever: still
sensed, still targetable, still physically integrated, just with a
`HullState.integrity` of 0 that almost nothing looked at. This was found
only while wiring the `ship_destroyed` replay event (Milestone 12 needs a
real "the ship is gone" moment to record one) -- worth flagging explicitly
as a caution for future passes: "every piece works when tested in
isolation" is not the same guarantee as "the pieces are actually wired
together", and this codebase's own test suite (28 files, all passing)
did not catch this because no existing test ever ran a hull down to
exactly zero through `tick_simulation` and then checked whether the ship
was still there afterward -- it is easy to write a thorough test for a
mechanic you know you built and never think to test for a consequence
you did not realize was missing.

Fix (`_resolve_ship_destruction`, see ARCHITECTURE.md for the full
design rationale): checked once per tick, ship removed via the
pre-existing `remove_ship` plus a new `FormationState.remove_member`
call this file's own formation code already exposed but
`SimulationWorld` never called on destruction. ASSUMPTION (INTERPRETATION,
not canon -- no Honorverse source specifies simulator bookkeeping):
removal happens one tick after the KILLING hit lands (mirrors
`_cleanup_inactive_missiles`'s existing timing convention exactly, see
ARCHITECTURE.md), and a missile already in flight toward a now-removed
ship keeps flying at its last physics state (frozen, not redirected or
despawned) rather than being retargeted -- a dead hulk not maneuvering
under its own power is physically sensible and required no new code
(GDScript's own refcounting keeps the `ShipPhysicsState` object alive via
`MissileState.target` even after `ships.erase()`).

## Milestone 12: commands vs. events, and why `ReplayLog` does not store a state snapshot

ASSUMPTION/INTERPRETATION: `ReplayLog` records COMMANDS (inputs, replayed
by re-calling the same public API) and EVENTS (outputs of resolution,
recorded for a future Battle Report/UI but never replayed/re-applied) as
two clearly separate arrays, never merged into one "things that happened"
timeline. Chose NOT to also record a snapshot of the initial ship/
formation/mount setup inside `ReplayLog` itself -- that setup already
lives in whatever scenario script builds it (no "Scenario" file format
exists yet, ТЗ §46/Milestone 13, honestly not started), so a `ReplayLog`
today is only meaningful paired with the SAME scenario-construction code
that produced the world it was recorded from, not a fully self-contained
file. This is a real, honestly-logged limitation, not an oversight: once
Milestone 13 (Scenarios) gives scenarios a real serializable format, a
replay file should probably embed (or reference) the scenario it was
recorded from so a saved `.json` replay is meaningful on its own without
also having the exact scenario-building script around -- left for that
future pass rather than inventing a scenario format prematurely just to
serve replay.

Честно НЕ сделано (см. CHANGELOG.md за полный список): STRUCTURAL_
INTEGRITY/POWER/DEFENSIVE_SYSTEMS без потребителя (см. выше); задержка
для `order_missile_launch` (сознательно мгновенна); зависимость задержки

## ЗАКРЫТО 2026-09-19: §33.1 Autonomous behavior during the succession window

## Формационное взаимное прикрытие ПРО (§22.1) -- спецификация есть, реализации нет

По сцене из книг, описанной пользователем (прорехи в ПРО одного
корабля прикрываются соседом по строю; разрыв строя обнажает прореху).
Прямая цитата не найдена несмотря на поиск в этой сессии (см.
CANON_RULES.md "Шестнадцатая сверка") -- правило INTERPRETATION,
собранное из уже принятых §41.1/§33.1/§61.

Для реализации, по шагам (честная оценка стоимости, по аналогии с
предыдущей записью для §33.1/§34.1/§34.2/§41.1):

* **Шаг 1 -- модель сектора стрельбы ПРО.** Сейчас `PointDefenseMount`
  всенаправленная (только `max_engagement_range_m`/`reaction_time_s`/
  `recharge_time_s`, см. point_defense_mount.gd) -- нет вообще понятия
  "откуда мимо этого корабля ПРО не достаёт". Можно переиспользовать
  уже существующий секторный словарь §41.1 (`AttackGeometry.Sector`,
  attack_geometry.gd) вместо изобретения нового.
* **Шаг 2 -- формационная проверка прикрытия.** `FormationState`
  (formation_state.gd) знает станционные офсеты, но не считает, какой
  сосед в данный момент физически способен прикрыть прореху данного
  корабля (нужна геометрия: относительное положение + сектор соседа).
  Это новая логика поверх существующей структуры, не косметика.
* **Шаг 3 -- фактическое влияние на резолюцию ПРО/клина.** Прикрытая
  прореха должна быть труднее пробить, чем непокрытая -- это правка
  `PointDefenseResolution`/резолюции клина с учётом результата шага 2.
* **Шаг 4 -- AI/целеуказание (§26/§34).** Противник должен УМЕТЬ
  целиться в непокрытую прореху предпочтительнее покрытой -- иначе
  правило существует только "для нас", что прямо нарушает §43.1 (одни
  правила для всех кораблей).

Самый дешёвый первый шаг -- Шаг 1 (переиспользует существующий
секторный код §41.1); Шаги 2-4 архитектурно взаимозависимы и полного
эффекта дают только вместе.


## Формационная координация распределения целей (§34.1) -- ЗАКРЫТО 2026-09-19

Реализовано `TacticalAI.select_formation_target_for_member` +
`SimulationWorld._resolve_formation_target_assignment` -- см.
CHANGELOG.md/ARCHITECTURE.md за этот день за полным описанием механизма.
Здесь -- явные числовые/понятийные ASSUMPTION этого прохода, честно
зафиксированные:

* **`MAX_USEFUL_ATTACKERS_PER_TARGET = 2`** -- ASSUMPTION (инженерный
  выбор, не канон): сколько формационных "соратников" считаются
  достаточным одновременным обстрелом одной цели этим тиком, прежде чем
  автоматика предпочтёт полностью свободную цель. Honorverse не даёт
  числовой канонической цифры "сколько кораблей реально усиливают друг
  друга по одной цели, прежде чем добавление ещё одного стрелка
  перестаёт быть полезным" -- это была бы функция от реальной боевой
  математики (урон за выстрел, сопротивление wedge/sidewall/брони,
  hit-вероятность), которую этот проект и так уже моделирует отдельно
  через `WeaponResolution`, поэтому дублировать её здесь как "прогноз
  результата" означало бы завести второй, неизбежно расходящийся
  источник истины. `2` выбрано как самое простое ненулевое число,
  различающее "один корабль стреляет" (нормально) от "уже есть компания,
  предпочти свободную цель, если она есть" -- требует пересмотра, если
  геймплей-тестирование покажет, что реальные бои с этим числом выглядят
  неестественно скученными или наоборот слишком разрозненными.
* **"Нейтрализована" = hull integrity fraction <= `CRITICAL_HULL_FRACTION`
  (0.3)** -- сознательно ПЕРЕИСПОЛЬЗОВАН тот же порог, что уже определяет
  "этот корабль критически повреждён и должен отступать" для СВОИХ
  кораблей (см. `TacticalAI.is_critically_damaged`), а не введено второе,
  отдельное число "насколько повреждён враг, чтобы прекратить его
  добивать". Семантически это разные вопросы (когда МОЙ корабль должен
  бежать vs когда ВРАЖЕСКИЙ корабль уже не стоит дополнительного
  внимания), но при отсутствии канонической причины использовать разные
  цифры для них, переиспользование одного уже принятого числа честнее,
  чем изобретать второе без обоснования -- тот же принцип уже применялся
  в §33.1 (is_guide_lost переиспользует is_critically_damaged).
* **Что НЕ смоделировано, честно.** Это НЕ прогноз "сколько тиков до
  уничтожения цели" и не учитывает реальный урон-в-секунду конкретных
  орудий/ракет, дистанцию до цели относительно эффективной дальности,
  или текущее состояние wedge/sidewall цели (степень защиты, а не только
  hull integrity). Корабль с почти полным hull, но полностью открытым
  бортом (сорванный sidewall) будет ошибочно считаться "полным здоровья"
  этим правилом -- честно оставлено как известное упрощение первого
  среза, не проблема для исправления этим проходом.
* §34.2 (Missile time-on-target, синхронизация подлёта ракет) --
  ПО-ПРЕЖНЕМУ НЕ сделано. Этот проход координирует только ВЫБОР цели,
  общий и для энергооружия, и для пусковых установок -- НЕ момент
  запуска ракеты и не время её подлёта к цели. §34.2 потребует отдельно
  вычислять время полёта ракеты (зависит от дистанции, разгона, манёвра
  цели) и по нему намеренно сдвигать момент запуска у разных
  ракетных установок формации, чтобы несколько ракет прибыли к цели
  одновременно -- отдельная, ещё не начатая задача.
* §41.1 (Crossing the T) -- по-прежнему не реализовано, не зависит от
  этого пункта (см. существующую запись выше, "Crossing the T / Doubling
  / TOT / succession-window initiative").
