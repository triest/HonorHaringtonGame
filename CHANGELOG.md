## 2026-09-19 (проход: §34.1 Doubling -- формационная координация распределения целей)

По списку пользователя от 2026-09-19 (по возрастанию номера раздела ТЗ,
после закрытия §33.1 предыдущим проходом) -- следующий по порядку пункт,
§34.1 Doubling, реализован. §34.2 (missile TOT) и §41.1 (Crossing the T)
по-прежнему открыты -- см. ниже.

* `tactical_ai.gd` -- новая чистая функция
  `TacticalAI.select_formation_target_for_member(ship, contacts,
  hostile_ids, hulls, assigned_counts, max_useful_attackers=2,
  critical_fraction=0.3)`. Тот же контракт "no cheat vision", что и у
  `select_weapon_target` (только USABLE контакты, дистанция по
  `estimated_position`), плюс два дополнительных координационных сигнала:
  цель, чей отслеживаемый hull integrity уже <= `critical_fraction` (тот
  же порог, что `is_critically_damaged` уже использует для СВОЕГО
  отступления -- переиспользован, а не изобретён заново), считается уже
  эффективно нейтрализованной; цель, уже "занятая" `max_useful_attackers`
  (ASSUMPTION, по умолчанию 2 -- канонической цифры "сколько кораблей
  реально усиливают друг друга по одной цели" не существует) или больше
  соратниками по формации в этом же тике, считается уже достаточно
  обстреливаемой. Трёхуровневый выбор (не занятая и не нейтрализованная →
  занятая, но не нейтрализованная → нейтрализованная) гарантирует, что
  корабль НИКОГДА не остаётся без цели просто потому, что все видимые
  враги оказались "невыгодными" -- честный fallback, тот же принцип, что
  и везде в этом модуле. При пустых `assigned_counts` и отсутствии
  нейтрализованных целей функция ТОЧНО повторяет `select_weapon_target`.
* `simulation_world.gd` -- новая функция `_resolve_formation_target_assignment`,
  выполняется в `tick_simulation` ПОСЛЕ `_resolve_damage_response` и ПЕРЕД
  `_resolve_weapons_ai`/`_resolve_missile_launch_ai`. Для каждой формации
  с действующим (не потерянным, `TacticalAI.is_guide_lost`) guide --
  "выполняется от лица guide-корабля в иерархии команд", как и требует
  формулировка §34.1 -- обходит участников в детерминированном порядке
  (guide, затем `member_offsets.keys()`) и для каждого, кто СПОСОБЕН сам
  выбрать цель в этот тик (есть команда/team, не критически повреждён, не
  под приказом "hold fire", и НЕ имеет активного ручного §30-назначения --
  явный приказ командира по-прежнему приоритетнее автоматики, та же
  иерархия приоритетов, что уже используется everywhere в этом файле),
  вызывает `select_formation_target_for_member` с общим для формации на
  этот тик счётчиком `assigned_counts`, так что выбор второго участника
  уже "видит" выбор первого -- настоящая последовательная координация, не
  просто одинаковые независимые догадки. Результат кладётся в новый
  словарь `_formation_assigned_targets[ship_id]`, полностью
  перестраиваемый каждый тик (без "залипания" между тиками).
* `_resolve_weapon_target` (общая политика выбора цели для энергооружия
  И пусковых ракет) расширена третьим приоритетом: (1) ручное §30-
  назначение, (2) координированное §34.1-назначение этого тика, (3)
  прежний автоматический "ближайший враг". Устаревшая/более не валидная
  запись на любом уровне честно проваливается на следующий -- тот же
  принцип, что уже был у ручного назначения.
* Формация без валидного guide (в процессе передачи командования, §33)
  НЕ получает координированного назначения в этот тик -- её участники
  просто используют прежний независимый fallback, ровно как до этого
  прохода (нет "фантомного координатора" для обезглавленной формации).
* `test_tactical_ai.gd` -- 6 новых unit-тестов на
  `select_formation_target_for_member` (вырождение в
  `select_weapon_target` без координации; уклонение от уже "занятой"
  цели при наличии свободной; всё равно выбор занятой/нейтрализованной
  цели, если других нет; деприоритизация нейтрализованной цели; null при
  отсутствии врагов). `test_formation.gd` -- 2 новых сквозных теста через
  `SimulationWorld.tick_simulation()`: формация guide+2 wing с двумя
  враждебными кораблями (один близкий, один далёкий) -- первые два
  участника в детерминированном порядке дублируют огонь по ближней цели
  (2 <= дефолтного cap), третий уходит на дальнюю, а не садится третьим
  на уже дважды занятую; отдельно -- формация без guide не получает
  координированного назначения вовсе. Итого 19 assertion-тестов в
  test_tactical_ai.gd (было 13), 113 в test_formation.gd (было 109), все
  29 headless-тестов проекта зелёные (Godot v4.3-stable, эта сессия,
  включая `--headless --path project --import` после правок без ошибок).

Честно НЕ сделано этим проходом (следующие кандидаты по списку
пользователя, по возрастанию): §34.2 Missile time-on-target -- этот
проход координирует только ВЫБОР цели, не момент запуска/подлёта ракет
к ней (staggered launch для synchronized arrival остаётся отдельной,
ещё не начатой задачей); §41.1 Crossing the T -- манёвренный
intercept-geometry solver по-прежнему не существует вообще, Tactical AI
всё ещё не умеет вычислять курс для выхода на выгодный угол, только
выбирает цель среди уже видимых контактов.

`update_trigger` практически в момент своего же повторного срабатывания,
хотя cron `59 */3 * * *` (минута 59, не 0) не должен подпадать под
описанное в документации инструмента поведение "anchor to now" (то
относится только к `0 * * * *`-подобным часовым паттернам). Причина
остаётся не выясненной до конца этой сессией — либо пользователь сам
вручную перезапускает задачу (`fire_trigger`) вскоре после завершения
предыдущего прохода, либо где-то раньше временно стоял более частый
cron и сейчас доигрывают уже запущенные с того момента долгие сессии.

## Расследование параллельного исполнения scheduled-задачи — итог этого прохода

По просьбе пользователя проверена конфигурация самого trigger'а
(`list_triggers`, доступно из облачной сессии, не только из
device_bash): зарегистрирован РОВНО ОДИН trigger
(`trig_01MR2jCcsytL2gPbDvhVgkG7`) с cron `59 */3 * * *` — это
ПРАВИЛЬНЫЙ, ожидаемый интервал ровно раз в 3 часа (минута 59: 00:59,
03:59, ..., 21:59), никаких признаков более частого срабатывания на
уровне конфигурации нет. `last_fired_at` этого прохода (21:59:42)
ровно на 3 часа позже характерного времени предыдущих упоминаний
(18:59 и т.д.) — расписание само по себе не является причиной
наблюдавшихся 4 подряд "чужих" коммитов.

предыдущими проходами): `create_trigger`/`list_triggers` не
гарантируют, что предыдущий запуск ЗАВЕРШИЛСЯ до следующего
срабатывания по расписанию — если один проход по какой-то причине
выполняется дольше 3 часов (завис, застрял на скачивании Godot при
плохой сети, долгий тестовый прогон и т.п.), следующее срабатывание
по cron стартует ПАРАЛЛЕЛЬНО с ещё не завершившимся предыдущим,
создавая ровно ту картину, что наблюдалась 4 раза подряд (два
экземпляра, оба видят один и тот же git-репозиторий, оба коммитят
независимо) — без необходимости в "ручных" перезапусках или
неправильном cron. Это НЕ подтверждено (нет доступа к точной
длительности предыдущих сессий из этой сессии), но это самое простое
объяснение, совместимое со всеми фактами (единственный trigger,
корректный cron, `updated_at`≈`last_fired_at` объясняется тем, что
предыдущий проход вызвал `update_trigger` в конце СВОЕЙ работы, что
могло совпасть по времени с ОЧЕРЕДНЫМ штатным cron-срабатыванием, а не
с чем-то аномальным). Рекомендация пользователю: если проходы
регулярно занимают около или больше 3 часов — либо увеличить интервал
cron, либо это стоит просто принять как известную особенность (не
критично: общий git-репозиторий, оба прохода коммитят независимо, как
уже отмечено в предыдущих записях).

## 2026-09-18 (проход: §29 Formation Orders — явные ПРИКАЗЫ формации, а не только пассивное holding)

Закрыт крупный честно залогированный пробел, упомянутый во многих
предыдущих записях подряд: "остальные явные §29 Formation Orders (change
course/speed/formation/attack/target distribution и т.д. как ИГРОВЫЕ
ПРИКАЗЫ) не реализованы — есть только пассивное formation-keeping".
Этот проход даёт формации реальные, выполняемые приказы для ведущего
корабля, поверх уже существующего member station-keeping (которое не
менялось).

* Новый файл `formation_order.gd` (`FormationOrder`, class_name):
  Kind-энум `HOLD_FORMATION` / `CHANGE_COURSE` / `CHANGE_SPEED`.
  `CHANGE_COURSE` замораживает текущую скорость ведущего в момент выдачи
  приказа и перенацеливает направление; `CHANGE_SPEED` замораживает
  текущий курс и перенацеливает величину скорости — вместе они
  покрывают весь кинематический список §29 (change course/change
  speed/accelerate/decelerate). `withdraw_orders()` — составной
  хелпер (не новый Kind): сначала развернуться от угрозы, затем
  разогнаться до скорости отхода — покрывает §29 "withdraw"/"disengage"
  как композицию двух примитивов, честно не новая механика. Статический
  `hold_formation()` — явный "прекратить манёвр" приказ.
* `FormationState`: новые поля `current_order`/`order_queue` (§35
  Command Queue: "Orders can be queued") + методы `issue_order`/
  `issue_orders`/`issue_order_now` (немедленно прерывает текущий и
  очищает очередь — для срочных приказов типа disengage)/`clear_orders`.
* `simulation_world.gd`'s новая `_resolve_formation_orders(dt)`,
  запускается ПЕРЕД `_resolve_formation_keeping` в `tick_simulation`:
  переводит активный приказ формации в `commanded_thrust_local`
  ведущего корабля. Закон выполнения — EXACT-STOP clamp: ускорение
  всегда направлено точно на остаточную ошибку скорости, а величина
  ограничена `min(max_accel, error.length()/dt)` — то есть ведущий
  никогда не проскакивает цель за один тик, что даёт гарантированную
  монотонную сходимость БЕЗ колебаний и БЕЗ подбора коэффициентов (в
  отличие от bang-bang, который на типичных для этого кода ускорениях
  в сотни g проскочил бы цель на первом же тике, и в отличие от
  PD-контроллера station-keeping'а, которому нужны подобранные
  K_P/K_D). `HOLD_FORMATION` — не разовый манёвр: он НЕ завершается
  сам, а каждый тик явно обнуляет собственный manoeuvring thrust
  ведущего, пока его не заменят другим приказом. Формация без приказов
  (текущее и очередь пустые) — полный no-op: thrust ведущего не
  трогается вообще, поведение идентично коду ДО этого прохода (обратная
  совместимость подтверждена отдельным тестом).

## 2026-09-18 (проход: §29 "change formation" — реальная смена геометрии строя на лету)

Закрыт честно залогированный пробел, упоминавшийся в каждой из предыдущих
нескольких записей: "change formation" (смена самой геометрии
`design_offsets` на лету, а не просто движение ведущего) отсутствовала —
приказы прошлого прохода (CHANGE_COURSE/CHANGE_SPEED/HOLD_FORMATION)
двигали только ведущего, но не могли переформировать саму форму строя.

* `FormationOrder`: новый Kind `CHANGE_FORMATION` + поле
  `new_offsets_local: Dictionary` (ship_id → Vector3 offset в локальном
  кадре ведущего). Новый статический конструктор `change_formation(offsets_local)`.
  Приказ переназначает офсеты станций ТОЛЬКО для кораблей, явно
  перечисленных как ключи словаря — не упомянутый существующий член
  строя остаётся на своей текущей станции без изменений (реальный приказ
  "раскрыть интервалы на левом фланге" не должен молча снимать со
  станции правый фланг). Ключ, которого раньше не было среди членов
  строя, добавляет НОВОГО члена на эту станцию — §29 не различает
  "перестроение" и "постановку новичка на станцию", оба случая — просто
  "офсет этого корабля теперь X".
* `SimulationWorld._resolve_formation_orders`: `CHANGE_FORMATION`
  обрабатывается как отдельный случай (аналогично HOLD_FORMATION) ДО
  общей проверки `is_complete`/`commanded_thrust_local` — приказ НЕ
  трогает тягу ведущего вообще (курс/скорость ведущего продолжаются как
  были), применяется через новый `_apply_change_formation` и СРАЗУ ЖЕ
  считается выполненным (снимается с очереди в тот же тик).
* `SimulationWorld._apply_change_formation` (новый метод): переносит
  `new_offsets_local` в `formation.member_offsets`, затем СНИМАЕТ СНИМОК
  результирующей полной геометрии (все текущие члены + ведущий=ZERO) как
  новый `formation.design_offsets`. Именно этот второй шаг — суть
  фичи: сам манёвр "долёта" до новой станции НЕ реализован отдельно —
  он полностью переиспользует уже существующий, уже протестированный
  PD-контроллер station-keeping (`_resolve_formation_keeping`,
  НЕ изменён в этом проходе), который в следующий тик увидит новый
  целевой офсет и сам полетит к нему — ровно так же, как он уже летит к
  design-станциям после передачи командования (§33). Никакой новой,
  отдельной "механики перестроения" не изобреталось — простота и
  консистентность (§43) вместо второй параллельной системы конвергенции.
* Перезапись `design_offsets` результатом (а не сохранение старой формы)

  так что ПОСЛЕДУЮЩАЯ передача командования (§33) должна перепланировать
  выживших вокруг формы, заданной ЭТИМ приказом, а не тихо откатываться
  к форме, существовавшей до него.

## Milestone 11: §30 "missile launch" as a discrete one-time order (`order_missile_launch`)

Closes the honestly-logged gap from the previous pass ("'missile launch'
as a distinct one-shot action separate from this standing posture"):
until now, the ONLY way anything fired missiles was the fully-automatic
`_resolve_missile_launch_ai` running every tick against each ship's
standing target (manual designation or automatic nearest-hostile) and
standing `weapons_free` posture. There was no way to say "fire a salvo at
THIS target right now" as a single, explicit, one-time action.

* New `SimulationWorld.order_missile_launch(ship_id: String,
  target_ship_id: String = "") -> int`: fires from every ready, in-range
  missile tube belonging to `ship_id` at the resolved target immediately,
  and returns the number of missiles actually launched. Does NOT touch
  the ship's standing `ShipCombatDirective` at all (leaves
  `manual_target_ship_id`/`weapons_free` completely unread-from-state and
  unwritten) — the automatic AI keeps using its own standing posture,
  unaffected, starting the very next tick. Empty `target_ship_id` falls
  back to the same standing-target resolution the automatic AI already
  uses (`_resolve_weapon_target`); a non-empty `target_ship_id` that
  isn't a currently usable hostile contact fires nothing and does NOT
  fall back to automatic selection — a one-time order names its target or
  fails, it doesn't get silently redirected (see ARCHITECTURE.md for the
  full fallback-policy comparison against the standing-designation case).
* Respects every existing physical/fire-control gate exactly like the
  automatic AI does: `weapons_free == false` suppresses it too (kept ONE
  consistent meaning for that flag everywhere), a critically damaged
  (disengaging) ship never launches, and tube readiness (ammo, cooldown,
  `condition`-scaled effective range) is never waived by an order —
  matches `fire_weapon()`'s existing convention for energy weapons.
* Callable directly (same "explicit shot trigger" convention `fire_weapon`
  already established), not wired into `tick_simulation`'s per-tick
  resolution loop at all — this is deliberate: a discrete order has no
  "converging" state to check across ticks, unlike the kinematic
  `IndividualOrder` queue (see ARCHITECTURE.md for why this did NOT
  become a new `IndividualOrder.Kind` or a new state class).
* New file `test_missile_launch_order.gd` (8 tests, 18 assertions):
  no-target falls back to standing/automatic selection; explicit target
  overrides the standing designation for one salvo WITHOUT mutating that
  standing designation (verified directly against
  `ship_combat_directives`); an invalid explicit target fires nothing and
  does not fall back; hold-fire suppresses the explicit order too;
  critically damaged ships don't launch; out-of-range targets don't
  launch; only ready tubes fire and the returned count matches exactly
  (a spent tube alongside a ready one); a nonexistent ship or a ship with
  no tubes returns 0 without error.

## 2026-09-19 (проход: §63.1 Ship Destruction — уничтоженные корабли теперь становятся обломками, не исчезают)

* `ShipPhysicsState.is_wreck: bool` — новый флаг. Никогда не читается
  `integrate()`/физикой напрямую (обломок продолжает интегрироваться
  ТОЧНО как любой корабль без тяги — момент импульса не исчезает, §12) —
  читается только резолверами `SimulationWorld`, каждый из которых
  теперь пропускает обломок целиком.
* `_resolve_ship_destruction()` переписан: вместо `remove_ship(ship_id)`
  — `ship.is_wreck = true`, `ship.commanded_thrust_local = Vector3.ZERO`
  (тяга обнуляется ОДИН раз — экипажа больше нет держать курс, но
  `velocity`/`angular_velocity` не трогаются вообще, инерция продолжается),
  `individual_orders`/`ship_combat_directives`/`ecm_states` для этого
  корабля стираются ("нельзя отдать приказ", §63.1), корабль убирается
  из member_offsets всех формаций (как и раньше). Корабль ОСТАЁТСЯ в
  `ships`/`hulls`/`sensor_contacts`/`teams` — §63.1 прямо требует, чтобы
  он оставался валидным sensor-контактом и персистентным объектом.

  в начале сбора списка уничтоженных) — иначе обломок с вечно
  `hull.is_destroyed()==true` писал бы `ship_destroyed` событие каждый
  тик заново.
* Обломок исключён из ВСЕХ боевых/командных резолверов явной проверкой
